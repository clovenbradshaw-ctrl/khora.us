# Changelog

## Unreleased

### Added
- `SPEC.md` — full specification for Khora as a bootstrap shell + protocol over Matrix rooms.
- `SPEC.md §14` — subscriptions and shared instances. Frames Khora as a master app users sign in to, with subscriptions (mounts) and instances (Matrix Spaces wrapping app+data) as the user-facing primitives. CRM/Airtable mental model crosswalk.
- `SPEC.md §15` — repo and room: development vs execution. The repo is source; the Matrix room is release. Bootstrap never reads from GitHub at runtime. CI is the publish step. Includes the publish pipeline, fork model across both layers, registry-as-seed pattern, and the honest-tension note on CI vendor centralization.
- `SPEC.md §16` — bootstrap UX surface. Three top-level surfaces (Mounts/Library/History), home-as-launcher-of-mounts, mirror-image Library for apps and data, fork modal, create-from-repo flow with `khora.json` repo config, schema-filtered mounting, three-lane history view, citation-as-event-ID-triple URLs, dense default with verbose toggle, settings drawer including the capability audit log. "One verb with arguments" framing.
- `SPEC.md §3.2` — optional `source` block on `m.room.app.manifest` (`repo`, `commit`, `tag`, `build_log`). Makes the repo↔room trust chain auditable end to end without making it required.
- `khora.json` repo config (referenced from §16.5) — minimal manifest declarations bootstrap reads from a source repo to drive create-from-repo. Schema lands in `schemas/` during Phase 0.
- `mxapp://` URI scheme (referenced from §16.3) — convenience scheme bootstrap accepts in the Add-by-URI input alongside room aliases and IDs.
- `STORAGE.md` — sibling spec for local persistence: IndexedDB layout (`events`, `state_current`, `checkpoints`, `indexes_live`, `sync`, `media`, `meta`), append-only changelog rules, schema-declared materializers, time-travel via `stateAt()`, capability-API additions for time-traveled queries and indexes, conflict/resync behavior, storage limits, EO operator alignment, and the invariants the cache must hold (determinism, recoverability, refetchability, time-travel exactness — all fuzz-testable). Treats `events` as REC ↬ made local; everything else is derivation.
- `SPEC.md §17` — standard surfaces and shared component library. Lifts EO-DB's component inventory into two layers: bootstrap-provided surfaces (member viewer, schema viewer, snapshot history, capability audit log, storage panel — every mount gets these for free) and a `@khora/ui` library apps opt into (universal views Table/Kanban/Calendar/Graph/Record/Horizon, EO-aware controls including operator filters and snapshot diff and REC trace, schema/constraint/resolution-policy editors, Notion-style block composition, collaboration surfaces). Adds `getOption`/`setOption` for cross-app user preferences with a frozen vocabulary (density, theme, operator badges, verbose, default view, audit verbosity). Migration path lifts EO-DB itself into the library so it consumes what it inspired.
- `SPEC.md §18` — peer-to-peer sync as a bootstrap responsibility. Every app gets P2P automatically; the capability API is transport-transparent. Pluggable transport stack (federation, embedded homeserver, WebRTC, mDNS, sneakernet, Pinecone), discovery via signaling rooms / well-known endpoints / local broadcast / manual exchange, single diagnostic method (`getTransport` / `getTransportFor`) for UX, partition-tolerance scenarios as first-class, plus Phase 8 (direct P2P) and Phase 9 (LAN + sneakernet) added to the phase plan.
- `SPEC.md §19` — easy app building, four tiers. Tier 0: layout-only apps (compose blocks, publish dashboard as an app, no code). Tier 1: `npx create-khora-app` scaffolds (view kind / schema / permissions wizard, emits a working repo against `@khora/ui` with publish workflow). Tier 2: `khora dev` with hot reload + embedded homeserver. Tier 3: in-bootstrap web IDE. Tiers 0 and 1 are concrete deliverables; 2 and 3 are roadmap. Held line: bootstrap renders blocks, scaffolds emit code, anything beyond is the app author's job.
- `SPEC.md §3.2.1` — additive layout-renderer manifest variant: `code: { renderer, layout_room, layout_state_key }` for Tier 0 apps. No fetched code, no `sha256` to verify; trust chain reduces to recognizing built-in renderer IDs.
- `SPEC.md §20` — the write contract. Ordered guarantees on every `append` regardless of entry path (hand-coded apps, Tier 0 dashboards, Tier 1 scaffolds, `<ImportView>`, CLI tools, P2P-merged inbound writes; the §21 entry below extends the path list to include `importHydration`). Schema validation, EO-triple injection, permission check, local-first changelog, externalization, server confirmation with idempotency, encryption, read-your-writes, P2P propagation, audit log capture. Failure surfaces enumerated; testable via the Phase 0 fuzz harness extending the STORAGE.md invariants. Forward-references added to §4.2 and §6.2.
- `tools/README.md` adds `create-khora-app/` and a view-kind catalog mapping wizard choices to `@khora/ui` components; `verify.ts` row updated to mention the §20 fuzz harness role.
- Repo layout in §9 adds a `templates/` directory for `create-khora-app` starter repos.
- README highlights now include easy app building (Tier 0 + Tier 1) and the write contract.
- `SPEC.md §6.2` rewritten as the canonical, complete capability API listing. All methods from §14, STORAGE §9, §17.4, and §18.5 now appear in one block (with `SnapshotMetadata` type defined inline). Notes transport-transparency and points readers to STORAGE.md and §17.4 for backing detail.
- `SPEC.md §21` — event size, externalization, and hydration. Generalizes §3.3's `mxc://` + `sha256` + `parts` pattern from app-code bundles to data events of any kind via schema-declared `externalizable_fields[]` (with optional gzip and per-blob AES-256-GCM encryption in E2EE rooms). Adds hydration on **two complementary paths**: room-shared (`m.room.hydration` state events referencing a `khora.hydration.v1` bundle, federates through Matrix) and **external encrypted hydration files** (standalone `.khr` files held outside Matrix entirely, covering disaster recovery, air-gap device provisioning, long-term cold storage, and cross-org handoff with out-of-band keys). External files support passphrase / hardware-key (WebAuthn PRF) / Shamir n-of-m split key modes; an optional `eo.user.hydration_index` audit breadcrumb records file metadata in the user's user room without ever exposing key material. New capability methods `exportHydration` and `importHydration` added to §6.2; `importHydration` replays through the §20 write contract. Bulk-import shape (`eo.import.batch` with thread-related children), backpressure semantics, orphan-blob GC policy, federation/sneakernet/fallback layering, and the materializer XOR rule (a field is either `externalizable_fields[]` or in `materializers[]`, never both) are specified.
- `SPEC.md §20.1` step 5 — "Externalize over-threshold fields" inserted between local changelog (step 4) and server send (now step 6); existing steps renumbered 5→6, 6→7, 7→8, 8→9, 9→10, 10→11. Atomic-rollback semantics: if any externalized blob fails to upload, the entire `append` is rolled back, the local changelog row is marked `failed`, and the upload queues for retry in `outbound_queue` (STORAGE §3.8). The §6.2 mention of "ten guarantees" is updated to "eleven."
- `SPEC.md §20.3` — two new failure surfaces: `PayloadTooLarge` (event still exceeds the homeserver cap after externalization, or no `externalizable_fields[]` declared on a field that needs them) and `MediaUploadFailed` (externalized blob upload failed; event not sent; retry queued).
- `STORAGE.md §3.7` — new `hydration` object store recording both room-shared and external-file hydrations applied to the local cache, with a `source` discriminator, `key_fingerprint` for external rows (never the key itself), and the deduplication ground for re-imports.
- `STORAGE.md §3.8` — new `outbound_queue` object store backing the §21.9 backpressure surface and SPEC §20.1 step 5 atomic-rollback semantics for failed externalization.
- `STORAGE.md §3.9` — existing `meta` store renumbered from §3.7. (Content unchanged.)
- `STORAGE.md §6.3.1` — hydration during restoration: bundles act as fast-fill checkpoints; subsequent `/sync` continues from `as_of_event`. Externalized field references resolve lazily via `media` (§3.6); the bundle's optional media-cache section pre-populates that store.
- `STORAGE.md §6.5` — new "Three sources, one cache" subsection distinguishing device-local checkpoints (§6, never sent over the wire), room-shared hydration (SPEC §21.5, federates), and external hydration files (SPEC §21.6, off-Matrix entirely). Imports from any of the three land equivalent state; provenance is preserved in `checkpoints.reason` and the `hydration` store.
- `STORAGE.md §10.2` — multi-device note extended to clarify that room-shared hydration federates while external hydration files travel out of band.
- `schemas/README.md` adds `m.room.hydration.json` (room-shared hydration) and `eo.user.hydration_index.json` (external-file audit breadcrumb), plus a section documenting the `externalizable_fields[]` schema amendment.
- `data-schemas/README.md` adds the `externalizable_fields[]` authoring convention and the materializer-XOR rule for schemas declaring large fields.
- `tools/README.md` adds `hydration/` (`khora-hyd`) — CLI wrapper for `exportHydration` / `importHydration` with `export`, `import`, `inspect` (no key needed), and `verify` (no decryption) subcommands; passphrase / hardware-key / split-key modes.
- `tools/hydration/` (`@khora/hydration`) — working implementation of the `khora.hydration.v1` bundle envelope and the external `.khr` file container. Bundle format: u32 manifest_len, UTF-8 JSON manifest, u32 section_count, then per-section (u8 type, u64 length, 32-byte SHA-256, payload bytes); per-section hashes let importers salvage prior sections when a later one is corrupt. File format: 8-byte magic `KHRAHYD1`, u16 version, u16 flags, u32 header_len, plaintext UTF-8 JSON header (bound into AEAD AAD), 12-byte AES-GCM nonce, AES-256-GCM ciphertext (with embedded tag), optional 64-byte Ed25519 signature. Implements passphrase mode (Argon2id → AES-256-GCM via `@noble/hashes` + WebCrypto) and Ed25519 signing; reserves hardware-key (WebAuthn PRF) and Shamir n-of-m split modes per SPEC §21.6 and rejects them with a clear error. CLI subcommands `export`, `import`, `inspect`, `verify` work end-to-end. 16 unit tests cover bundle round-trip, per-section hash detection, raw-key + passphrase round-trips, wrong-passphrase fingerprint-fail, header-tampering AEAD detection, signing + verify, and rejection of reserved key modes. Package is private, ESM, plain JS to match the repo conventions.
- `package.json` adds `@noble/hashes` (zero-dep, audited, pure-JS Argon2id implementation that runs in both Node and browsers).
